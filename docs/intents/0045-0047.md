# Intent #45 / #47: Daily aggregated AI cost + cost per model

Context: Issues [#45](https://github.com/luanmorenommaciel/oteru/issues/45) and [#47](https://github.com/luanmorenommaciel/oteru/issues/47) track the cost aggregation pipeline: daily cost totals per actor, daily cost breakdown by model, and trend visualization.

## Retenção e lookback (Alicerce)

**Retention strategy**: raw OTLP telemetry (`otel.otel_logs`, `otel.otel_traces`, `otel.otel_metrics_*`) carries the collector's default hot TTL (`OTERU_HOT_TTL=72h` from `oteru-collector-config.clickhouse.yml`). 

**Final design (duas tabelas físicas)**:
- `fct_cost_daily` (grain: `day_utc x model_family`) - **permanent**, no TTL, no actor_id. Historical business metrics, indefinite retention, privacy by design.
- `fct_cost_actor_daily` (grain: `day_utc x actor_id`) - **90-day TTL** (configurable via dbt var). Actor-specific attribution with automatic expiry, data minimization enforcement.

**Lookback window**: dbt incremental models use a 48-hour lookback (`cost_lookback_hours=48` in `oteru-dbt/dbt_project.yml`). On each run, the models delete and re-insert rows for the last 48 hours from the staging layer (`stg_api_request`), which reads from raw `otel.otel_logs` while they are still within the 72h hot TTL. The strict inequality **lookback < TTL** (48h < 72h, leaving 24h margin) ensures that no raw rows expire before the incremental can pull them. This is enforced by `scripts/check_cost_retention.sh` (run via `make check-cost-retention`).

**Out of scope**: backfilling from the cold archive (dual retention, [#85](https://github.com/luanmorenommaciel/oteru/pull/85)) is NOT wired into the dbt pipeline. If a user needs to recover cost data older than 72h, they must query the S3 archive directly (via ClickHouse `s3()`) or re-ingest it. Any backfill automation requires explicit owner approval and is deferred to a future issue.

**Guardrails** (`scripts/check_cost_retention.sh`, `make check-cost-retention`):

1. **No TTL on permanent aggregates**: `fct_cost_daily` (permanent) must have no TTL clause in `system.tables.engine_full`. If one appears, the check fails — historical cost data would be lost.
2. **Raw TTL preserved**: `otel_logs`, `otel_traces`, and `otel_metrics_sum` must carry their 72h TTL. If any table is missing its TTL, the check fails (regression).
3. **Lookback < TTL**: the dbt `cost_lookback_hours` (read from `oteru-dbt/dbt_project.yml`) must be strictly less than `OTERU_HOT_TTL`. If `lookback >= TTL`, the check fails — incremental deletes would operate on partially-expired data.
4. **Expiry safety test** (test-only): with a test ClickHouse, after raw rows of the oldest day expire, a new dbt run must NOT change that day's aggregate total. Validates the lookback logic.
5. **Actor tables must have TTL**: Any `fct_cost*` table with `actor_id` column (detected dynamically) must have TTL <= 90 days. Any permanent table without TTL cannot have `actor_id` column (privacy by design: actor attribution is time-limited, permanent aggregates are anonymized).
6. **Actor TTL preserves permanent totals** (test-only): When actor-specific rows expire (90-day TTL in `fct_cost_actor_daily`), permanent aggregate totals in `fct_cost_daily` (without `actor_id`) must remain unchanged. Validates the separation between actor attribution and permanent business metrics.

**Coordination**: `cost_lookback_hours` is defined in the dbt project config (`oteru-dbt/dbt_project.yml`, under `vars:`). The infra checks read this value; the dbt models reference it via `{{ var('cost_lookback_hours') }}`. Both sides must agree on the name and unit (hours).

## Staging view: `otel.stg_api_request`

**Location:** `oteru-collector/clickhouse/views/stg_api_request.sql`

**Type:** Plain `CREATE OR REPLACE VIEW` (non-materialized, applied by `make views`)

**Purpose:** Lift `claude_code.api_request` log events from `otel.otel_logs` into
typed columns for downstream aggregation by dbt.

### Schema

One row per `api_request` log event with the following columns:

- `event_ts` (DateTime64(9)) — event timestamp from `timeUnixNano`
- `observed_ts` (DateTime64(9)) — observation timestamp from `observedTimeUnixNano`
- `request_id` (String) — API request identifier from `LogAttributes['request_id']`
- `session_id` (String) — session correlation from `LogAttributes['session.id']`
- `model_raw` (String) — model name from `LogAttributes['model']`
- `cost_usd_micros` (Int64) — cost in USD micros: `toInt64(round(LogAttributes['cost_usd'] * 1e6))`
- `input_tokens` (Int64) — from `LogAttributes['input_tokens']`
- `output_tokens` (Int64) — from `LogAttributes['output_tokens']`
- `cache_read_tokens` (Int64) — from `LogAttributes['cache_read_tokens']`
- `cache_creation_tokens` (Int64) — from `LogAttributes['cache_creation_tokens']`
- `actor_id` (String) — collector-pseudonymized identity from `LogAttributes['user.email']`. The format is owned by the collector (currently `sha256:v1:<hex>`; a later commit will switch to `hmac:v1`). The view only passes the value through.
- `service_name` (String) — from `ServiceName`
- `dedup_key` (String) — deduplication key (see below)
- `has_empty_request_id` (UInt8) — boolean flag, 1 when `request_id` is empty

### Filter rules

- **Event type:** `Body = 'claude_code.api_request'`
- **Exclude synthetic:** `ResourceAttributes['oteru.traffic'] != 'synthetic'` (PR #96)
- **No raw user fields:** No `user.email` plaintext, no `user.*` except the pseudonymized `actor_id`
- **No content:** No prompt or response content in any column

### Deduplication strategy

The view does **not** deduplicate — it is read-only. Deduplication happens downstream
in dbt's `int_api_request_dedup` (one row per `request_id`, earliest `observed_ts`).

**Dedup key logic:**
- When `request_id` is non-empty: use it directly
- When `request_id` is empty: hash of `(session_id, event_ts, model_raw, input_tokens, output_tokens)`
- Exposed as `dedup_key` column so dbt can partition on it
- `has_empty_request_id` flag allows counting and monitoring of empty cases

**Idempotency note:** The emitter's `restamp` function (in
`oteru-emitter/oteru_emitter/rewrite/restamp.py`, lines 145-152) rotates `request_id`
values during replay to avoid backend deduplication. This means two replays of the same
capture produce distinct `request_id` values and become distinct events. For idempotency
testing, **compare two runs over the same already-stored data**, not two replays.

## Downstream schedule (dbt implementation)

The dbt agent implements the following schedule:

- **Frequency:** Hourly run at :15
- **Lookback:** 48 hours by `event_ts` (reprocessing window)
- **TTL boundary:** 48h lookback stays inside the 72h raw data retention
- **Late data:** Events arriving >48h after their `event_ts` are dropped and counted
- **Retry policy:** 3 attempts with exponential backoff (30s, 2m, 8m)

## dbt Transformation Layer

### Overview

The `oteru-dbt/` project implements daily cost aggregation (#45) and model-level breakdown (#47) using dbt-clickhouse. It consumes `otel.stg_api_request` and produces incrementally-maintained fact tables (`fct_cost_daily` is permanent / no TTL; `fct_cost_actor_daily` has a 90-day TTL). `actor_id` arrives already pseudonymized by the collector (format owned by the collector; will change to `hmac:v1` in a later commit); the staging view and dbt models only pass it through.

### Model Architecture

#### Intermediate Layer

**`int_api_request_dedup`**
- **Purpose**: Deduplicates by `dedup_key`, keeping earliest `observed_ts`
- **Grain**: One row per `dedup_key`
- **Incremental**: 48h lookback via `{{ var('cost_lookback_hours') }}`
- **Engine**: `MergeTree()` with `allow_nullable_key: 1` (dedup_key is Nullable from view)
- **Order**: `(event_ts, dedup_key)`
- **Tests**: `unique` and `not_null` on `dedup_key`, `not_null` on all metrics

**Acceptance**: From Duto's 10-row fixture (9 non-synthetic, 2 req_001 duplicates):
- **8 rows** after dedup ✓
- **682950 micros** total (806400 - 123450 duplicate) ✓

#### Fact Layer

**`fct_cost_daily`** (#45, #47)
- **Grain**: `day_utc` × `model_family` (NO actor_id)
- **Purpose**: Permanent cost history by model, NO TTL
- **Absorbed `fct_cost_by_model_daily`**: that third table was never merged. By-model cost is this table; daily total is the sum over `model_family`. No third table is needed, and nothing downstream broke.
  ```sql
  -- by-model view (the table itself)
  SELECT day_utc, model_family, cost_usd_micros
  FROM otel.fct_cost_daily
  ORDER BY day_utc, model_family;

  -- daily total = sum over model_family
  SELECT day_utc, SUM(cost_usd_micros) AS total_cost_usd_micros
  FROM otel.fct_cost_daily
  GROUP BY day_utc
  ORDER BY day_utc;
  ```
- **Model mapping**: `model_aliases.csv` seed (`model_raw` → `model_family`)
- **Unmapped models**: Labeled `'unmapped'`
- **Derived**: `day_utc = toDate(event_ts, 'UTC')`
- **Metrics**:
  - `cost_usd_micros` (Int64 sum, source of truth)
  - `cost_usd` (Float64, `cost_usd_micros / 1e6` for display)
  - `requests` (distinct `dedup_key` count)
  - Token sums: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`
- **Incremental**: `ReplacingMergeTree()`, delete+insert last 48h. Empty existing tables load everything (`count() = 0` guard); an unguarded `max(day_utc) - INTERVAL` is NULL and drops all rows.
- **NO TTL**: Historical data preserved indefinitely
- **Tests**: unique grain, `not_null` on all columns

**`fct_cost_actor_daily`**
- **Grain**: `day_utc` × `actor_id`
- **Purpose**: Per-actor cost for active monitoring
- **Metrics**: Same as `fct_cost_daily`
- **Incremental**: `ReplacingMergeTree()`, delete+insert last 48h. Same empty-table `count() = 0` guard as `fct_cost_daily`.
- **TTL**: `ttl='day_utc + INTERVAL ' ~ var('actor_cost_ttl_days', 90) ~ ' DAY'` (dbt-clickhouse `ttl` config key so it lands in `CREATE TABLE`; nested `{{ var() }}` inside `config()` is not rendered). Default 90 days, provisional pending Vinícius.
- **Tests**: unique grain, `not_null` on all columns

**`fct_cost_trend`** (#45)
- **Type**: View over `fct_cost_daily` (permanent table only)
- **Metrics**:
  - `daily_cost_usd`: total per day
  - `cost_7d_avg`: 7-day moving average
  - `cost_wow_change_pct`: week-over-week % change

#### Seeds

**`model_aliases.csv`**: Maps common model names to families:
- `claude-opus-4-8` → `claude-opus-4`
- `claude-sonnet-4-5` → `claude-sonnet-4`

#### Analyses (Reconciliation & Freshness)

**`reconciliation_daily_vs_staging.sql`**
- **Purpose**: Daily aggregate vs staging source reconciliation
- **Tolerance**: max(0.5%, 10000 micros) per closed UTC day
- **Closed day**: At least 1 day in past (allows 48h late arrivals)
- **Returns**: Only rows exceeding tolerance (empty = all reconciled)

**`freshness_check.sql`**
- **Purpose**: Lag between aggregate's latest partition and max(event_ts) in staging
- **Thresholds**: 2h warning, 6h incident
- **Returns**: Status (OK/WARNING/INCIDENT) + lag metrics

### Audit Trail

**`audit_cost_runs`** on-run-end hook:
- **Table**: `otel.audit_cost_runs` (MergeTree)
- **Columns**:
  - `run_id`, `run_started_at`, `run_completed_at`, `duration_seconds`
  - `rows_processed`: Count from `int_api_request_dedup`
  - `max_event_ts_read`: Latest event processed
  - `events_dropped_late`: Count >48h late (via `{{ var('cost_lookback_hours') }}`)
  - `rows_empty_request_id`: Count from `has_empty_request_id` flag
  - `run_status`: success/warning/failed

**Note**: Hook is enabled (`on-run-end: log_run_audit` in `dbt_project.yml`). Both clocks are UTC so `duration_seconds` is non-negative; `dbt_command` comes from `invocation_args_dict`. The hook ends with `SELECT 1` so dbt-clickhouse does not see an empty query.

### Edge Cases Handled

1. **Midnight boundary** (23:59:59 / 00:00:00 UTC):
   - `toDate(event_ts, 'UTC')` partitions correctly
   - Fixture includes events at day boundaries (verified in manual testing)

2. **Late arrivals**:
   - Events arriving 48h+ after `event_ts` enter correct day on next run (within lookback)
   - Events arriving 72h+ are dropped by TTL (counted in `events_dropped_late`)

3. **Empty `request_id`**:
   - View generates MD5 hash as `dedup_key`
   - `has_empty_request_id` flag tracks occurrence
   - Audit hook counts them per run

4. **Idempotency**:
   - Two consecutive `dbt build` runs over same data → identical row counts and totals
   - Verified manually: run1 and run2 produce zero diff
