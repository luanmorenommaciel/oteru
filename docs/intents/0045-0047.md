# Intent #45 / #47: Daily aggregated AI cost + cost per model

Context: Issues [#45](https://github.com/luanmorenommaciel/oteru/issues/45) and [#47](https://github.com/luanmorenommaciel/oteru/issues/47) track the cost aggregation pipeline: daily cost totals per actor, daily cost breakdown by model, and trend visualization.

## Retenção e lookback (Alicerce)

**Retention strategy**: raw OTLP telemetry (`otel.otel_logs`, `otel.otel_traces`, `otel.otel_metrics_*`) carries the collector's default hot TTL (`OTERU_HOT_TTL=72h` from `oteru-collector-config.clickhouse.yml`). The dbt-built aggregate fact tables (`fct_cost_daily`, `fct_cost_by_model_daily`) have **no TTL** — they are incrementally maintained and must preserve historical data indefinitely.

**Lookback window**: dbt incremental models use a 48-hour lookback (`cost_lookback_hours=48` in `oteru-dbt/dbt_project.yml`). On each run, the models delete and re-insert rows for the last 48 hours from the staging layer (`stg_api_request`), which reads from raw `otel.otel_logs` while they are still within the 72h hot TTL. The strict inequality **lookback < TTL** (48h < 72h, leaving 24h margin) ensures that no raw rows expire before the incremental can pull them. This is enforced by `scripts/check_cost_retention.sh` (run via `make check-cost-retention`).

**Out of scope**: backfilling from the cold archive (dual retention, [#85](https://github.com/luanmorenommaciel/oteru/pull/85)) is NOT wired into the dbt pipeline. If a user needs to recover cost data older than 72h, they must query the S3 archive directly (via ClickHouse `s3()`) or re-ingest it. Any backfill automation requires explicit owner approval and is deferred to a future issue.

**Guardrails** (`scripts/check_cost_retention.sh`, `make check-cost-retention`):

1. **No TTL on aggregates**: `fct_cost_daily` and `fct_cost_by_model_daily` must have no TTL clause in `system.tables.engine_full`. If one appears, the check fails — historical cost data would be lost.
2. **Raw TTL preserved**: `otel_logs`, `otel_traces`, and `otel_metrics_sum` must carry their 72h TTL. If any table is missing its TTL, the check fails (regression).
3. **Lookback < TTL**: the dbt `cost_lookback_hours` (read from `oteru-dbt/dbt_project.yml`) must be strictly less than `OTERU_HOT_TTL`. If `lookback >= TTL`, the check fails — incremental deletes would operate on partially-expired data.
4. **Expiry safety test** (stub, test-only): with a short `OTERU_HOT_TTL_TEST=1h`, after raw rows of the oldest day expire, a new dbt run must NOT change that day's aggregate total. This check is skipped in normal runs (needs a throwaway ClickHouse and a sleep > TTL) but is a regression test for the lookback logic.

**Coordination**: `cost_lookback_hours` is defined in the dbt project config (`oteru-dbt/dbt_project.yml`, under `vars:`). The infra checks read this value; the dbt models reference it via `{{ var('cost_lookback_hours') }}`. Both sides must agree on the name and unit (hours).

## Staging view: `otel.stg_api_request`

**Location:** `oteru-collector/clickhouse/views/stg_api_request.sql`

**Type:** Plain `CREATE OR REPLACE VIEW` (non-materialized, applied by `make views`)

**Purpose:** Lift `claude_code.api_request` log events from `otel.otel_logs` into
typed columns for downstream aggregation by dbt.

### Schema

One row per `api_request` log event with the following columns:

- `event_ts` (DateTime64(9)) — event timestamp from `timeUnixNano`
- `observed_ts` (DateTime64(9)) — observation timestamp from `observedTimeUnixNano`
- `request_id` (String) — API request identifier from `LogAttributes['request_id']`
- `session_id` (String) — session correlation from `LogAttributes['session.id']`
- `model_raw` (String) — model name from `LogAttributes['model']`
- `cost_usd_micros` (Int64) — cost in USD micros: `toInt64(round(LogAttributes['cost_usd'] * 1e6))`
- `input_tokens` (Int64) — from `LogAttributes['input_tokens']`
- `output_tokens` (Int64) — from `LogAttributes['output_tokens']`
- `cache_read_tokens` (Int64) — from `LogAttributes['cache_read_tokens']`
- `cache_creation_tokens` (Int64) — from `LogAttributes['cache_creation_tokens']`
- `actor_id` (String) — pseudonymized identity from `LogAttributes['user.email']` (PR #94)
- `service_name` (String) — from `ServiceName`
- `dedup_key` (String) — deduplication key (see below)
- `has_empty_request_id` (UInt8) — boolean flag, 1 when `request_id` is empty

### Filter rules

- **Event type:** `Body = 'claude_code.api_request'`
- **Exclude synthetic:** `ResourceAttributes['oteru.traffic'] != 'synthetic'` (PR #96)
- **No raw user fields:** No `user.email` plaintext, no `user.*` except the pseudonymized `actor_id`
- **No content:** No prompt or response content in any column

### Deduplication strategy

The view does **not** deduplicate — it is read-only. Deduplication happens downstream
in dbt's `int_api_request_dedup` (one row per `request_id`, earliest `observed_ts`).

**Dedup key logic:**
- When `request_id` is non-empty: use it directly
- When `request_id` is empty: hash of `(session_id, event_ts, model_raw, input_tokens, output_tokens)`
- Exposed as `dedup_key` column so dbt can partition on it
- `has_empty_request_id` flag allows counting and monitoring of empty cases

**Idempotency note:** The emitter's `restamp` function (in
`oteru-emitter/oteru_emitter/rewrite/restamp.py`, lines 145-152) rotates `request_id`
values during replay to avoid backend deduplication. This means two replays of the same
capture produce distinct `request_id` values and become distinct events. For idempotency
testing, **compare two runs over the same already-stored data**, not two replays.

## Downstream schedule (dbt implementation)

The dbt agent implements the following schedule:

- **Frequency:** Hourly run at :15
- **Lookback:** 48 hours by `event_ts` (reprocessing window)
- **TTL boundary:** 48h lookback stays inside the 72h raw data retention
- **Late data:** Events arriving >48h after their `event_ts` are dropped and counted
- **Retry policy:** 3 attempts with exponential backoff (30s, 2m, 8m)

## Acceptance criteria

The e2e test (`scripts/check_signals_e2e.sh`) asserts:

1. **8 distinct dedup keys** after dedup (from 10-row fixture with 2 duplicates by `request_id`)
2. **Synthetic exclusion:** 9 rows visible (1 synthetic excluded from 10-row fixture)
3. **Cost accuracy:** Exact sum of `cost_usd_micros` matches expected total
4. **No PII leakage:** No column contains '@' character

The dbt test asserts that `int_api_request_dedup` produces exactly 8 rows from the fixture.
